# CheckStock

Веб-прототип учёта остатков на складах фулфилмента: где физически лежит товар,
сколько доступно, что зарезервировано под FBS, что едет между ФФ и что уже
отправлено на маркетплейс или клиенту.

**Стек:** Python 3.12, FastAPI, SQLAlchemy 2, PostgreSQL, Jinja2, Docker Compose.
Для быстрого локального запуска поддерживается SQLite — код один и тот же.

---

## Быстрый запуск

### Вариант 1: Docker + PostgreSQL (рекомендуется)

```bash
docker compose up --build
```

Открыть <http://localhost:8000>. PostgreSQL поднимается в контейнере, демо-данные
загружаются автоматически. Порт БД на хосте — `5433`, чтобы не конфликтовать с
локальным PostgreSQL.

### Вариант 2: локально на SQLite (без Docker)

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux/macOS:
# source .venv/bin/activate

pip install -r requirements.txt
python -m app.seed --reset
uvicorn app.main:app --reload
```

Приложение: <http://127.0.0.1:8000>. Файл БД — `checkstock.db` в корне проекта.
Если БД пустая, демо-данные создаются при старте (`AUTO_SEED=true`).

### Тесты

```bash
pytest -q
```

Тесты используют отдельную SQLite-базу `test_checkstock.db` и не трогают
демо-данные. Покрыты все ключевые сценарии задания, включая нехватку, удаление
склада с остатком и повторное подтверждение.

## Демо-данные

Один магазин, два ФФ. Количества соответствуют заданию:

| Артикул | Товар | Север | Юг |
|---|---|---:|---:|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

Итого 25 единиц. Пересоздать данные: `python -m app.seed --reset`.

## Экраны

| Экран | Что показывает |
|---|---|
| **Остатки** (`/`) | Все товары × ФФ: физически, резерв FBS, доступно. Отдельные блоки: товар между ФФ, FBO в пути, FBO на маркетплейсе, FBS к клиенту. Сводные итоги. |
| **Склады** (`/warehouses`) | Добавление, переименование и мягкое удаление ФФ. У архивного склада остатки и история сохраняются. |
| **Движения** (`/movements`) | Приход, отправка перемещения, приёмка (в том числе частичная), матрица доступных остатков. |
| **Отправки** (`/shipments`) | Резерв FBS (отправка/отмена), FBS в доставке, FBO в пути с приёмкой, FBO на маркетплейсе. |
| **История** (`/history`) | Неизменяемый журнал: товар, количество, откуда/куда, дата, комментарий, фильтры. |

Дополнительно: `GET /api/stock` — read-only JSON-срез остатков, `GET /healthz`.

## Как устроен учёт

### 1. Остаток = сумма операций, а не редактируемое поле

Таблицы `operations` хранят текущее состояние операции, `operation_events` —
неизменяемый аудит-лог. Физический остаток, резерв и «в пути» вычисляются из
журнала (`services/stock.py`). Поэтому:

- остатки всегда сходятся после каждого действия;
- историю нельзя «потерять» отдельно от остатка;
- любую цифру можно объяснить конкретными операциями.

### 2. Состояния операций

| Операция | Жизненный цикл | Влияние на остаток |
|---|---|---|
| Приход | `COMPLETED` | + к физическому остатку ФФ |
| Перемещение | `IN_TRANSIT → COMPLETED` | при отправке − с ФФ-отправителя; при приёмке + на ФФ-получатель; разница уходит в недостачу |
| Резерв FBS | `ACTIVE → FULFILLED / CANCELLED` | уменьшает «доступно», физический остаток не меняет |
| Отправка FBS | `SHIPPED → DELIVERED` | − с ФФ, товар числится «к клиенту», затем у клиента |
| Отправка FBO | `IN_TRANSIT → COMPLETED` | − с ФФ при отправке; + на маркетплейс только после приёмки |
| Недостача | событие | списание в `lost`, баланс остаётся сходимым |

### 3. Защита от повторного подтверждения

Каждая операция имеет `idempotency_key` с уникальным индексом. Ключ приходит из
скрытого поля формы. Повторная отправка того же запроса:

- находит уже созданную операцию и возвращает её;
- не создаёт вторую операцию и не списывает товар дважды;
- для приёмки дополнительно проверяется статус (`COMPLETED` → no-op).

Гонка на уровне БД закрывается уникальным индексом, а изменения остатков одного
товара сериализуются через `SELECT ... FOR UPDATE` (PostgreSQL).

### 4. Нехватка на выбранном ФФ

Отрицательный остаток невозможен. Если на выбранном складе не хватает единиц,
операция отклоняется, а сообщение показывает:

- сколько доступно на выбранном ФФ;
- сколько есть на других складах;
- предложение сначала оформить перемещение.

Сценарий «на выбранном ФФ не хватает, но суммарно по складам достаточно» покрыт
тестом `test_shortage_at_selected_ff_with_stock_elsewhere`.

### 5. Удаление склада

Удаление — мягкое (`is_archived`). Что происходит:

- новые приходы, резервы и отправки в архивный склад запрещены;
- остаток остаётся в учёте и виден на экране остатков с пометкой «архив»;
- остаток можно вывезти перемещением на активный склад;
- история сохраняет имя склада на момент операции (снимок в событии).

### 6. Частичная приёмка

При приёмке перемещения или FBO можно указать меньше отправленного. Разница
фиксируется как недостача и списывается, остатки продолжают сходиться.
Это проверяется тестами `test_transfer_send_and_receive`,
`test_fbo_flow_with_partial_acceptance`.

## Проверка вручную (сценарий для видео)

1. **Приход.** Движения → SKU-102 «Контейнер», Юг, 7 ед. На экране остатков
   у Юга станет 7.
2. **Перемещение и недостача.** SKU-101, Север → Юг, 4 ед. После отправки:
   Север 6, в пути 4, Юг 6. При приёмке указать 3: Юг станет 9, появится
   недостача 1, «в пути» обнулится.
3. **Нехватка.** Попробовать отправить 10 ед. SKU-101 с Юга (доступно 9):
   операция отклонится, в сообщении будет остаток на Юге и на Севере.
   На чистом seed-сценарии: 8 ед. с Юга при 6 на Юге и 10 на Севере.
4. **FBS.** Отправить 3 ед. SKU-101 в резерв на Севере: физически 6, доступно 3.
   Отменить резерв → доступно снова 6. Создать снова и отправить клиенту:
   физически 3, товар в блоке «Клиенту по FBS». Нажать «Доставлено».
5. **FBO.** Отправить 2 ед. SKU-101 на маркетплейс: физически −2, товар
   «FBO в пути». Принять 1: на маркетплейсе 1, недостача 1.
6. **Удаление склада.** Склады → удалить «Юг». Остатки Юга (6 + 4 на seed)
   останутся на экране остатков с пометкой «архив», сумма не изменится.
   Новый приход на архивный склад запрещён, вывоз перемещением — разрешён.
7. **Идемпотентность.** Отправить форму прихода, вернуться назад и отправить
   ещё раз (или дважды нажать кнопку): второй запрос покажет, что операция уже
   проведена, остаток не изменится.
8. **История.** Показать журнал: приход, отправка/приёмка, недостача, резерв,
   FBS/FBO, фильтры по товару/складу/типу.

## Ключевые решения и компромиссы

- **Ledger вместо поля `quantity`.** Чуть дороже по вычислениям, зато остатки,
  история и недостачи не расходятся. Для прототипа объёмов достаточно.
- **Мягкое удаление склада.** Иначе остаток «исчезает» и баланс ломается.
- **Идемпотентность на уровне БД.** Уникальный ключ, а не только проверка в коде:
  защищает от гонок и двойных кликов.
- **`create_all` вместо Alembic.** Осознанный компромисс для тестового на один
  день; для промышленной эксплуатации первым шагом добавить миграции.
- **Один магазин.** По заданию; модель `Store` уже есть, поэтому переход к
  нескольким магазинам — вопрос фильтрации и прав доступа, а не переделки схемы.
- **Нет авторизации.** В прототипе не требуется; в README не выдаётся за готовое
  к продакшену.
- **SQLite-фолбэк.** Позволяет проверить проект без Docker; основной вариант —
  PostgreSQL в `docker-compose`.

## Использование ИИ

Проект собран с активным использованием ИИ: генерация каркаса, шаблонов и
тестов, затем ручная проверка бизнес-правил. Что проверялось отдельно:

- сходимость остатков после каждой операции (инвариант в тестах: сумма по всем
  локациям + доставлено + недостачи = все приходы);
- невозможность отрицательного остатка и текст ошибки при нехватке;
- повторная отправка формы с тем же ключом;
- удаление склада с остатком и сохранение истории;
- частичная приёмка и списание недостачи.

Все сценарии зафиксированы в `tests/test_inventory.py` и проходят локально и в
Docker-окружении.
